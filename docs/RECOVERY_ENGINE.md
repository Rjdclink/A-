# Customer recovery engine

The public dashboard remains passwordless. Revenue recovery now includes real customer cases alongside the existing public website research and lead-outreach tools.

## Five implemented improvements

1. **Priority queue:** checkout, cart and inquiry signals receive explainable intent scores with a bounded contribution from merchant-supplied opportunity value. This is a rules-based starting point, not a trained conversion-probability model. Website research retains its AI analysis, evidence and confidence.
2. **Grounded outreach:** deterministic drafts quote the recorded journey and return URL. Optional AI drafts use event/CRM evidence and require explicit review and approval. New evidence invalidates old approvals. Failed AI requests produce a labeled template fallback. Application-generated unsubscribe links cannot be removed by AI output.
3. **Adaptive sequences:** default email at 2 and 24 hours, SMS at 48 hours, with configurable delays, channel-specific consent, frequency limits, holdouts and stop-on-purchase/reply/opt-out. Automatic sending defaults off. Scheduled Neon tasks and POST invocations advance due messages. The engine claims each step before contacting a provider; uncertain delivery blocks retries for provider review. Accepted does not mean delivered.
4. **Payment recovery:** read-only Stripe invoice sync plus signed invoice webhooks fetch current invoice state, including next retry. Stripe Billing owns Smart Retries and failed-payment emails. Enable those in the linked Stripe recovery settings; A+ does not alter provider retry configuration or initiate extra charges. Invoice sync scans at most 500 open invoices per request and reports truncation; individual invoice refresh is available. Stripe webhook events keep known invoice statuses current.
5. **Measured improvement:** stable customer-level randomized holdouts and A/B message styles. Reports separate currencies and include only complete observation windows. Incremental revenue is the difference in revenue per enrolled mature customer times treatment size, can be negative, and is explicitly exploratory. Copy comparisons reuse the existing conservative minimum-sample checks and unadjusted exploratory rate test. Choose a copy mode for a new experiment; running cohort policies are immutable. No autonomous model retraining or causal certainty is claimed.

## Setup in the dashboard

Settings → Service setup stores supplied provider settings encrypted, with secrets omitted from reads:

- Existing AI endpoint/model/key and SMTP configuration.
- `RECOVERY_PUBLIC_URL`: public HTTPS dashboard origin for unsubscribe links. The hosted Neon deployment supplies its existing public origin by default.
- `RECOVERY_TWILIO_SID`, `RECOVERY_TWILIO_TOKEN`, `RECOVERY_TWILIO_FROM`: SMS account and sender.
- `RECOVERY_TWILIO_WEBHOOK_URL`: exact externally configured inbound webhook URL. Configure Twilio incoming messages to POST to `/api/recovery/webhooks/twilio`. Signed STOP and other opt-out keywords suppress matching contacts; other replies stop follow-ups for review.
- `RECOVERY_STRIPE_KEY`: read access for invoices. `RECOVERY_STRIPE_WEBHOOK_SECRET`: signing secret for `/api/recovery/webhooks/stripe`. Subscribe to `invoice.payment_failed`, `invoice.updated`, `invoice.paid`, `invoice.voided`, `invoice.marked_uncollectible`.

These account credentials are optional during installation. Readiness reports configuration, not live verification. No real customer emails, SMS messages or charges are generated by the test suite or deployment.

## Event contract

All routes use the existing workspace scope. The hosted public deployment allows only `default` for dashboard APIs. Provider webhooks target that hosted workspace and always require provider signatures, independent of dashboard access.

POST `/api/recovery/engine/contacts`:

```json
{"customer_id":"customer-42","email":"buyer@example.com","phone":"+15551234567","email_consent":true,"sms_consent":false,"consent_source":"Checkout email opt-in recorded 2026-10-25"}
```

POST `/api/recovery/engine/signals`:

```json
{"id":"checkout-42","customer_id":"customer-42","type":"checkout","amount_cents":4200,"currency":"USD","return_url":"https://store.example/checkout","evidence":"Customer requested this checkout; merchant event checkout-42"}
```

Supported signals: `cart`, `checkout`, `lead`, `purchase`, `reply`, `opt_out`. IDs must be stable; duplicates are ignored. Use identical customer IDs across systems. Stripe invoice monitoring is independent of marketing enrollment. Website scans and public contact emails do **not** imply marketing consent and do not automatically enroll contacts in customer sequences.

Purchase events arriving through `/api/events` and signed Shopify paid-order webhooks automatically stop customer sequences if they include the matching `customerId` / Shopify customer ID. Other storefronts/CRMs can post normalized signals through the endpoint above using the existing HTTP workflow step. This release does not silently install storefront scripts or subscribe to third-party merchant webhooks without their account setup.

POST a `purchase` signal with a unique order ID and amount to record an outcome. Matching purchases stop all active customer follow-ups, including holdouts. A single first purchase is attributed to the latest eligible case within its observation window; currencies must match for reporting. One customer enrolls once per experiment; overlapping experiment windows are rejected. Changing a sequence requires a new experiment name, except pausing/resuming it.

Email replies must be forwarded by the merchant's mail/CRM integration as `reply` or `opt_out` signals, or recorded with the dashboard outcome form. This release does not poll arbitrary SMTP inboxes. Email unsubscribe links show a confirmation form; POST stops the contact. Re-importing contacts cannot silently undo an opt-out.

Customer privacy export/erase includes engine contacts, cases and deliveries. Erasure deletes identifiable recovery records and stores a hashed suppression marker to prevent re-enrollment. Workspace removal also clears all engine tables. Invoice records are provider billing records, managed separately from customer recovery identifiers.

## Verification

`npm run verify` includes controlled provider tests for ranking, generated drafts, review gates, event deduplication, timing, consent, frequency limits, holdouts, ambiguous deliveries, Stripe signature freshness/current-state retrieval, Twilio Basic/form protocol and signed STOP, erasure and durable Neon state. Provider fixtures do not prove real-account permissions or deliverability. Test the compiled bundle and production read-only routes after deploying.
